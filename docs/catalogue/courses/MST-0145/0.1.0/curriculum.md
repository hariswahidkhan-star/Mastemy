## Learning outcomes

1. Describe scaling Scrum with the Nexus framework
2. Apply cross-team dependency management and integration
3. Evaluate the Nexus events and the integrated Increment
4. Analyse reducing cross-team complexity and improving flow at scale

## Sample items (original, draft, unreviewed)

**MST-0145-Q0001** (single-answer, Select ONE) Several teams on one product each finish their own work but only integrate at the very end, causing failures. Nexus addresses this by emphasising:

- A. Continuous integration and managing cross-team dependencies throughout the Sprint **(key)**  
  _Rationale:_ Correct: Nexus focuses on integration and dependency management to produce one Increment.
- B. Each team shipping separately with no integration  
  _Rationale:_ Separate shipping is exactly the problem.
- C. Adding more handoffs between teams  
  _Rationale:_ Nexus reduces, not adds, integration friction.
- D. Delaying all integration until release  
  _Rationale:_ Deferred integration causes the crunch.

**MST-0145-Q0002** (single-answer, Select ONE) The Nexus Integration Team exists primarily to:

- A. Coordinate and coach teams so they produce one integrated Increment **(key)**  
  _Rationale:_ Correct: the NIT focuses on integration across teams.
- B. Do all the coding for every team  
  _Rationale:_ The NIT coordinates; it does not do all the work.
- C. Replace the Product Owner  
  _Rationale:_ The NIT does not replace the Product Owner.
- D. Manage individual performance reviews  
  _Rationale:_ That is not its purpose.

**MST-0145-Q0003** (multiple-answer, Select TWO) Which TWO practices most reduce cross-team integration problems at scale? (Select TWO)

- A. Identifying and sequencing dependencies during cross-team refinement **(key)**  
  _Rationale:_ Correct: surfacing dependencies early prevents late collisions.
- B. Integrating work frequently rather than at the end **(key)**  
  _Rationale:_ Correct: frequent integration avoids a release crunch.
- C. Letting each team define its own private Definition of Done  
  _Rationale:_ Inconsistent 'done' breaks integration.
- D. Avoiding any cross-team communication  
  _Rationale:_ Isolation increases integration risk.
- E. Deferring integration testing to after release  
  _Rationale:_ Late testing finds failures too late.
